# bpsc-cmo v0.2.0 — module navigation and authenticated surveys

## Changes

The Evaluation System is an internal module. Public directory routes, profile views, controller actions, navigation links and publication controls have been removed. `/` redirects guests to login and authenticated users to Dashboard. All Evaluation routes require an active signed-in account and module authorization.

Dashboard and Administration are the common shell. Dashboard offers an Evaluation System module card. Module links appear only while visiting `/modules/evaluation`; they do not persist on Dashboard, Profile or Administration pages. Module permissions also apply to direct URLs and POST/PUT/DELETE requests. Future modules can add their own route file under `routes/modules/` and register it inside the authenticated route group.

## Current access

| Role | Common features | Evaluation module |
| --- | --- | --- |
| Administrator | Dashboard, own account, users, roles, designations, units, audit logs | Expert pool; survey/question CRUD; participant-role selection; all responses |
| Chairman | Dashboard and own account | Active surveys assigned to Chairman; submit evaluations; own responses |
| Member | Dashboard and own account | Active surveys assigned to Member; submit evaluations; own responses |
| Staff | Dashboard and own account | Expert pool CRUD |

## Survey workflow

1. Administrator creates a survey as Draft, including title, instructions and participant roles (Chairman, Member or both).
2. Add questions to that survey; each question has its own required/optional flag, active status and display order.
3. Activate the survey after adding at least one active question. Draft and Closed surveys cannot be attended, including by submitting an already-open form. Removed surveys are unavailable; old responses remain.
4. An eligible Chairman/Member opens Available Surveys, chooses Attend Survey, selects an expert and viva date, and submits answers. Responses retain immutable survey, question, expert and evaluator snapshots.

Survey participation currently follows the earlier expert-evaluation workflow. The initial expert/viva-date fields remain. Duplicate prevention is now per survey + evaluator + expert + viva date, allowing the same expert/day to be evaluated in separate surveys. Later board/session rules can extend this workflow.

## Question types

| Type | Input / validation |
| --- | --- |
| Select Field | One option from a dropdown |
| Date Selection | Date input, default current Bangladesh date; validated as YYYY-MM-DD |
| Time Selection | Time input; validated as HH:mm, 24-hour time |
| Rating (1 to 5) | One integer between 1 and 5 |
| Text Field | Single-line input, maximum 255 characters |
| Text Area | Multiline input, maximum 5,000 characters |
| Radio Button | One option from a radio group |
| Multiple Select | One or more checkbox options; duplicate/unknown options rejected |

Option-based questions accept 2–50 distinct labels, each up to 200 characters. Required multiple-select groups require at least one selection. Optional questions may be skipped. Cross-survey question IDs, stale questionnaires and wrong answer types are rejected server-side. Date questions can use any valid date; the viva-date field separately retains its no-future-date rule.

## Update from v0.1.0

1. Back up the project and database.
2. Extract the Paste & Replace ZIP into the existing **bpsc-cmo project root**. Keep your `.env` and existing dependencies. Prebuilt frontend assets are included.
3. Run:

```bash
php artisan optimize:clear
php artisan migrate
```

4. Sign in and open Dashboard → Evaluation System.

The migration preserves all existing users, experts, questions and evaluation answers. If v0.1.0 questions/responses exist, they are grouped under an active **Initial Expert Evaluation** survey, available to Chairman and Member. Existing `choice` questions become Radio Button; existing multiline `text` questions become Text Area. Submitted answer snapshots are not rewritten. The old publication column is retained only for database compatibility and is no longer read or editable.

The removed public Blade files may remain physically on an installation updated by copying files. They have no routes or controller actions and cannot be accessed as a public directory. Optionally delete `resources/views/directory/` and `resources/views/layouts/public.blade.php` to match the current source tree. Do not expose `resources/` through your web server; the document root remains `public/`.

Fresh installations should use the full-project ZIP and follow README.md.
